# Supabase migration plan

Working document for moving Arrakit onto Supabase (Postgres with RLS, Realtime, Storage) while
keeping Better Auth as the identity provider and pg-boss as the job runner. Delete this file when
the last phase lands; the code and its tests are the record after that.

## Outcome

- Supabase is the backing service for Postgres, Realtime and Storage. Neon-specific notes, the
  LISTEN task feed, the SSE stream, RustFS and the standalone Mailpit script are gone.
- pg-boss stays for jobs, events and schedules, in its own `pgboss` schema on the Supabase
  Postgres. Supabase Queues (pgmq) and Cron are not used.
- Better Auth stays the only sign-in system. Supabase Auth runs (it cannot be turned off) but
  issues nothing.
- One permission model. The Better Auth access-control matrix in `@arrakit/auth/permissions` is the
  single source; it is turned into claims once, and the same claims are enforced by the API
  middleware, by RLS on every table, by Realtime channel policies and by Storage policies.
- Everything runs against the local Supabase stack (`supabase start`), in dev and in e2e.

## What the research found

### Better Auth and Supabase Auth

Supabase services (Data API, Realtime, Storage) authorise a request from a JWT: the `role` claim
picks the Postgres role and the rest is readable in policies through `auth.jwt()`. There are four
ways to make Supabase accept a Better Auth user:

| Option                        | How                                                                                                                                               | Verdict                                                                                                                                                                                                                                                                              |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Third-party auth, Custom OIDC | Better Auth's JWT plugin signs the token; Supabase trusts Better Auth's issuer through OIDC discovery and JWKS, and only ever sees the public key | **Chosen.** The path Supabase's own Better Auth guide documents. The CLI has no `config.toml` option for it and the issuer must be HTTPS, so locally the same trust is set up by listing Better Auth's public key in the emulator's keys file. Billed per third-party MAU on hosted. |
| JWT signing keys              | The API signs with an ES256 key generated by the Supabase CLI (`signing_keys_path` locally, imported key on hosted)                               | Not chosen, kept as the fallback: documented and verified locally, but the API and Supabase share a private key.                                                                                                                                                                     |
| Claims inside a transaction   | The API connects to Postgres directly and sets `request.jwt.claims` and the role per transaction; no token involved                               | **Chosen for the API's own queries.** It is what the Data API itself does on every request.                                                                                                                                                                                          |
| Legacy HS256 JWT secret       | Sign with the shared project secret                                                                                                               | Rejected: deprecated by Supabase.                                                                                                                                                                                                                                                    |

The reverse direction (Better Auth as a Custom OAuth/OIDC sign-in provider for Supabase Auth)
would create a second user table and a second session, so it is not used.

Supabase publishes a guide for Better Auth ("Set up Better Auth with Supabase Declarative
Schema"). This plan follows it except where the local emulator rules it out:

| Supabase's guidance                                                                                    | This plan                                                                                                                                                                                  |
| ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Better Auth connects to the Supabase Postgres directly                                                 | Same.                                                                                                                                                                                      |
| Better Auth's tables live in a `better_auth` schema, outside the exposed one                           | Adopted for the identity and OAuth tables (decision 9).                                                                                                                                    |
| Migrations go through the Supabase CLI, never `auth migrate`                                           | Same, generated by drizzle-kit instead of the Better Auth CLI because the schema is already in Drizzle.                                                                                    |
| Policies read the user with `auth.jwt()->>'sub'`, not `auth.uid()`                                     | Same (`app.user_id()`).                                                                                                                                                                    |
| RLS for the Data API through third-party auth and Better Auth's JWT plugin, tested on a hosted project | Same on hosted. The guide says this cannot run on the CLI; locally Better Auth's public key goes in the emulator's keys file, so the token and the code path are the ones production uses. |
| Server code reads the session and filters its queries by user                                          | Kept, with RLS underneath. Supabase documents RLS over a direct connection with a per-request setting in its "RAG with Permissions" guide.                                                 |

So the integration has two halves that share one claims object:

- **Server path.** The API keeps its direct Postgres connection through Drizzle. Every
  organization-scoped operation runs in a transaction that first sets the claims and switches to
  the `authenticated` role, so RLS applies to the API's own queries.
- **Browser path.** For Realtime (and any direct Storage use) Better Auth's JWT plugin signs a
  10-minute ES256 token carrying the same claims, and Supabase verifies it with Better Auth's
  public key. `supabase-js` receives the token through its `accessToken` option.

### Unifying permissions

Before phase 1 tenancy was a convention (every query filtered by `organization_id`) and
permissions were checked only in the API. The unified model:

- Claims: `{ sub, role: 'authenticated', org_id, permissions: ['file:read', ...], actor }`, built by
  one function from the existing `permissionsOf(role, customRoles)`. Static roles and the
  per-organization dynamic roles both flow through it, so the database never needs to know role
  definitions.
- SQL helpers in a non-exposed `app` schema: `app.org_id()`, `app.user_id()` (text: user ids are
  `text` columns holding UUID values, so `auth.uid()` is not used), `app.has_permission(text)`.
- Every table has RLS enabled. Tenant tables get an isolation policy
  (`organization_id = (select app.org_id())`, both `using` and `with check`) plus permission gates
  on writes. Better Auth's identity and OAuth tables move to a `better_auth` schema with RLS on
  and no policy, so only the privileged connection (the Better Auth adapter, workers) reaches them.
  The one exception is `users`: member and team lists join it, so it gets a `select` policy
  limited to people who share the caller's organization, and a column-level grant (id, name, email,
  image).
- The API middleware keeps its checks (they give the 403/404 the contract promises); RLS is the
  guard underneath, and the only guard on the surfaces the browser reaches directly.

A token issued by Supabase Auth has no top-level `org_id` claim (a user cannot set top-level
claims), so it matches no policy. Sign-ups are disabled anyway.

### Verified on the local stack

Run on 2026-11-12 with CLI 3.1.0 (Postgres 17.11, Supavisor 2.10, Realtime 2.154, Storage 1.90)
and pg-boss 12.38:

- A token issued by Better Auth's JWT plugin (ES256 key pair, `auth.api.signJWT`, custom claims
  including `role`) is accepted by the Data API and by Realtime once Better Auth's public JWK is
  appended to `supabase/signing_keys.json` and the stack is restarted. RLS read the organization,
  the text user id and the permissions from it. A token from an unlisted key, or forged with a
  listed `kid`, is refused. Public-only entries in that file are observed behaviour on CLI 3.1.0,
  not a documented feature.
- The fallback also works: a token signed with the CLI-generated key is accepted by the Data API,
  Realtime and Storage (that JWK needs `key_ops`, `use` and `ext` removed before `jose` imports it
  for signing).
- RLS over the direct connection works with one statement at the start of the transaction:
  `select set_config('request.jwt.claims', $1, true), set_config('role', 'authenticated', true)`.
  The `postgres` role has `bypassrls`, so the switch is what makes RLS apply.
- `realtime.send(payload, event, topic, true)` inside a transaction is delivered only on commit. A
  private channel is joined only when a `select` policy on `realtime.messages` matches
  `realtime.topic()`; another organization's topic is refused.
- The client must `await supabase.realtime.setAuth()` before subscribing to a private channel. The
  channel outlives its first token (the client calls `accessToken` again on each heartbeat) as long
  as the token lives longer than the 25 s heartbeat: a 20 s token dropped, a 45 s token did not.
- pg-boss runs on the Supabase Postgres through the repository's own wrapper, over the direct
  connection and over the transaction-mode pooler: send, event fan-out, retry, dead letter,
  schedules and a send inside a Drizzle transaction all work, with no errors reported.
- Under the `authenticated` role a transactional send is refused (no privilege on the `pgboss`
  schema) and `realtime.send` is blocked by RLS. Enqueueing works when the jobs adapter resets the
  role for its own statement and restores it: the job exists only if the transaction commits, and
  RLS is back in force for the next statement. Broadcasting needs a `security definer` wrapper.
- Storage: a signed upload URL takes a plain `PUT` with the file as body; the token lasts 2 hours
  and is not configurable. Bucket-level `file_size_limit` and `allowed_mime_types` are enforced on
  that upload (413 and 415). `info()` returns size and content type; signed download URLs carry the
  attachment name.
- The bundled Mailpit answers its HTTP API on port 54324, which is what the API's dev mailer uses.
- PGlite (the test database) enforces RLS with roles and per-transaction claims.

### Platform changes to respect

- New tables are not exposed to the Data API without an explicit `GRANT` (enforced on all projects
  since 2026-10-30). Migrations grant explicitly.
- The `realtime` schema is locked (2026-07-14): no create, alter or drop, even as `postgres`.
  Policies on `realtime.messages` still work, and are the only thing migrations add there.
- CLI v3 targets the local stack by default; hosted commands need `--remote` and `--yes` in CI.

## Decisions and assumptions

1. **Better Auth signs the browser token; Supabase only knows its public key.** On hosted that is
   Custom OIDC, the path Supabase's Better Auth guide documents. Locally, where the CLI has no such
   option, the public key is listed in the emulator's keys file, so the token, the claims and the
   code are the same in both. The JWT plugin signs with EdDSA today (MCP tokens); the Supabase
   token needs ES256. The signer sits behind one function, and a key generated by the Supabase CLI
   and shared with the API remains the verified fallback.
2. **The Supabase CLI owns migrations.** drizzle-kit keeps generating them from the Drizzle schema,
   into `supabase/migrations` with the `supabase` prefix; hand-written SQL (functions, policies on
   `realtime.messages`, extensions) goes in custom migrations in the same folder. The API stops
   migrating at boot. This is what makes `supabase start`, `db reset`, `db push` and branching work.
3. **The existing eight migrations are squashed into one baseline.** Assumes no deployed database
   holds data worth keeping. If one does, keep the history instead and move the data with
   `pg_dump`/`pg_restore` in the last phase.
4. **Unit and integration tests stay on PGlite**, with a "Supabase prelude" that creates what the
   platform provides (roles, `auth.jwt()`, a `realtime.messages` table with `realtime.send` and
   `realtime.topic`). RLS and pg-boss are the real thing there; only Realtime is a stand-in. A
   small stack suite and the e2e suite run against the real local stack and catch drift. The
   alternative (every test on the Docker stack) needs the same stand-in for any non-default
   database and makes `pnpm test` depend on Docker.
5. **The Data API is not used.** The web keeps calling only `/api/*` through oRPC. The Data API is
   switched off; RLS and explicit grants are defence in depth.
6. **pg-boss stays; Supabase Queues is not adopted.** pgmq only stores and hands out messages. The
   retry limit, backoff, dead letters, event fan-out and schedules the code uses today would have
   to be rebuilt and tested by hand. pg-boss keeps them, runs on the Supabase Postgres unchanged
   and keeps running on PGlite in tests. The cost: jobs do not show in the Supabase Queues
   dashboard, and pg-boss manages its own schema outside `supabase/migrations`.
7. **Realtime carries change signals, not rows.** The browser refetches through oRPC, so the
   visibility rules for tasks stay in one place.
8. **Dev and e2e share one local stack.** E2e isolates itself with unique emails and organizations,
   as it already does for mail.
9. **Better Auth's identity and OAuth tables live in a `better_auth` schema** (`users`, `sessions`,
   `accounts`, `verifications`, `jwks`, `oauth_*`), as Supabase's guide recommends. They hold
   sessions, tokens and signing keys; a schema that is never exposed and never granted protects
   them even if `public` is exposed by mistake on a hosted project. The organization plugin's
   tables (`organizations`, `members`, `invitations`, `teams`, `team_members`,
   `organization_roles`) stay in `public`: they are tenant data that scoped queries and policies
   read.

## Phases

Each phase ends with `pnpm typecheck`, `pnpm lint`, `pnpm test` and `pnpm test:e2e` green, and with
`AGENTS.md` updated for what changed.

### Phase 0. Local stack and migrations

Landed. The app runs on the local Supabase stack, the Supabase CLI applies the migrations, and
Better Auth's identity and OAuth tables are in the `better_auth` schema. Two things turned out
differently from the plan and matter to the next phases:

- An empty `[api].schemas` does not unexpose `public` (the CLI falls back to it), so the Data API
  is switched off locally with `[api] enabled = false`. Realtime, Storage and Studio do not need
  it. On hosted the same is a project setting.
- `auto_expose_new_tables = false` keeps `select`, `insert`, `update` and `delete` from `anon` and
  `authenticated`, but new `public` tables still grant them `truncate`, `trigger` and
  `references`. Phase 1 revokes those.

### Phase 1. Tenancy and permissions in the database

Landed. Every table in `public` and `better_auth` has RLS on; the tenant policies and their
permission, ownership and actor gates live in the Drizzle schema, and the `app` helpers, revokes,
grants and default privileges in a custom migration. Every organization operation runs in a
transaction under the `authenticated` role with the caller's claims, and a generic test proves
isolation for every tenant table. Points that turned out differently from the plan and matter to
the next phases:

- The scope API is `forOrganization(claims)` for a person and `asSystem(organizationId)` for server
  work (workers, the Stripe webhook, the task watch hub, the auth hooks), not
  `forOrganization(id, actor)`: the organization comes from the claims' `org_id`, so the two cannot
  disagree. `claimsFor` in `@arrakit/auth/permissions` returns
  `{ sub, role: 'authenticated', org_id, permissions, actor: 'user' }`, the object phase 2 signs.
  System claims can only be built inside `packages/db`, so the signer cannot produce one.
- A fourth helper, `app.is_system()`, gates writes that no permission names (task moves, credit
  purchases and reversals, invitation email state), and `app.has_permission` is true for the
  system actor, so system claims carry no permission list.
- Reads are tenant-only; gates apply to writes. Internal reads (storage level, workspace delete,
  the watch hub) must see every row of the organization whatever the caller may read.
- Per-schema default privileges cannot take `EXECUTE` away from `PUBLIC` (they only add to the
  global defaults). The migration revokes execute on the existing `app` functions; a function
  added later, such as `app.broadcast` in phase 2, needs its own `revoke ... from public` and an
  explicit `grant ... to authenticated`.
- `better_auth.users` is readable only for people who share the caller's organization (column
  grant on id, name, email and image), so the names of people who left answer null
  (`uploaderName`, `creatorName`, `requesterName`, `publisherName`).
- The jobs adapter reads the current role, resets it for pg-boss's own statements only when it is
  not `none`, and restores the role it found; it is the only place that resets the role.
- A policy refusal is not mapped to a 403: reaching one means a missing middleware check, so it is
  an unexpected error. USING failures are silent (zero rows); WITH CHECK failures raise 42501.
- Custom roles are read on the privileged path before the scope is built; the MCP caller's
  permissions are computed eagerly (one indexed query per request for a custom role).
- Policies key on the `org_id` claim and there is no `iss` restriction yet; the server path sets
  claims without an issuer. Phase 2 or 4 decides whether policies check the issuer once Better
  Auth's tokens reach Supabase.
- PGlite runs a newer Postgres major (18) than the stack (17), and its user is a superuser while
  the stack's `postgres` is not. The pooler-backed concurrency suite and e2e cover the stack.
- Database advisors on the local stack report nothing caused by this phase's policies or
  functions. Left for phase 4: `function_search_path_mutable` on six `pgboss` functions (owned by
  pg-boss), unindexed foreign keys and unused indexes (informational), and
  `rls_enabled_no_policy` on the `better_auth` tables, which is intended.

### Phase 2. Realtime instead of SSE

Outcome: task changes reach the browser through Supabase Realtime; the LISTEN feed, the watch hub
and the `tasks.watch` stream are deleted.

- Token: give the JWT plugin an ES256 key and add one function in `@arrakit/auth` that calls
  `signJWT` with the claims and a 10-minute expiry. Two points to settle first: whether the ES256
  key is added next to the EdDSA one (`keyPairConfigs`) or replaces it for MCP tokens too, and how
  the dev key stays stable across `supabase db reset` (the plugin's key adapter fed from the
  environment, or re-exporting after a reset).
- Local trust: the setup script exports the public key from `/api/auth/jwks` into
  `supabase/signing_keys.json`; the stack reads that file at start.
- New contract procedure, member-only, returning the Supabase URL, the publishable key, the token,
  its expiry and the topics the caller may join.
- Custom migration: `app.broadcast(topic, event, payload)`; `select` policies on
  `realtime.messages` for two topic shapes: `org:<org_id>:tasks` (requires `task:read`) and
  `org:<org_id>:user:<user_id>:tasks` (the caller's own). No insert policy, so clients cannot send.
- Data layer: `tasks.notify()` calls `app.broadcast` in the writing transaction instead of
  `pg_notify`.
- Web: `@supabase/supabase-js` behind one module (`lib/realtime.ts`) that owns the client, the
  token cache and `setAuth`. `useTaskWatch` keeps its behaviour on top of it: refresh on
  `SUBSCRIBED` (today's `resync`), refetch on a signal, the existing backoff and polling fallback
  on `CHANNEL_ERROR`, `TIMED_OUT` and `CLOSED`, and closing while the page is hidden.
- Lint: `@supabase/supabase-js` may be imported only by that web module and by `packages/db`.
- Remove `packages/db/src/tasks/feed.ts`, `apps/api/src/tasks/watch.ts`, the `watch` procedure,
  the `taskFeed` health probe and `DATABASE_DIRECT_URL` (nothing needs a session connection once
  LISTEN is gone). Document that the browser now also talks to the Supabase origin (websocket),
  which a future `connect-src` must allow.

Tests: API tests assert the broadcast row is written with the change and vanishes on rollback; web
tests fake the realtime module; the e2e task spec subscribes through the real stack, receives a
signal and is refused another organization's topic.

### Phase 3. Storage on Supabase Storage

Outcome: files live in a private Supabase bucket; RustFS and the S3 SDK are removed.

- `packages/db/src/storage/supabase.ts` implements `Storage` with the secret key: signed upload
  URL, signed download URL with the download name, `info` for head, server-side upload for the MCP
  tool, remove, and a paginated list for prefix removal. The object layout (`<org_id>/...`) and the
  upload contract (`{ url, headers, expiresAt }`) do not change, so the web keeps its plain `PUT`.
- Limits: a signed upload URL does not bind size or type, so the bucket carries the widest plan
  limit and `completeUpload` checks the stored size and type against the plan and deletes an object
  that breaks it. Upload links last 2 hours instead of 15 minutes; the pending-file expiry job
  already covers abandoned uploads.
- `storage.objects` keeps deny-by-default (no policy): every access goes through a URL the API
  signed after its checks. Organization-scoped policies were verified and can be added when a
  feature needs direct client access.
- Env: `SUPABASE_URL` and `SUPABASE_SECRET_KEY` replace the `R2_*` variables. Remove
  `scripts/rustfs.sh`, its Turborepo task and the e2e server entry.

Tests: `memoryStorage()` stays for unit tests; the S3 integration test becomes a stack test; the
e2e file journeys run unchanged.

### Phase 4. Hosted project, hardening, cleanup

Outcome: a documented path to a hosted project, and no leftovers.

- Stack suite (`pnpm test:stack`): the checks from "Verified on the local stack" as tests (token
  accepted, tenant isolation over the wire, channel refusal, a job round trip through the pooler,
  storage limits).
- Hosted checklist in the README: create the project, `supabase link`, `supabase db push --remote`,
  add a Custom OIDC integration under Third-Party Auth with the Better Auth issuer
  (`<web origin>/api/auth`) and confirm a token is accepted (the first run of that path outside
  the emulator), disable sign-ups and providers in
  Supabase Auth, switch Realtime to private channels only, switch off the Data API, set the bucket
  limits. `DATABASE_URL` is the transaction pooler; the app needs no direct connection.
- Run the database advisors (`supabase db advisors`) and fix what they report; add it to the
  checks a change runs.
- Remove `@aws-sdk/*`, the PGlite runtime path and its env variables, the Neon notes and the
  data-only lint entries that no longer apply. Update `README.md`, `AGENTS.md`, both
  `.env.example` files, the Turborepo env pass-through, `scripts/init.ts` (the stack's
  `project_id`) and `docs/next-steps.md`. Delete this file.

## Risks

- **Extra round trips.** A scoped operation costs `begin`, the claims statement and `commit`.
  Acceptable for a starter; measure before optimising.
- **Stale browser tokens.** A permission change reaches Realtime when the token is next refreshed
  (at most 10 minutes). The API path has no such delay because it builds claims per request.
- **Prelude drift.** The PGlite stand-in for Realtime can diverge from the platform. The stack
  suite and e2e are the check.
- **Custom OIDC is unproven until a hosted project exists.** Supabase must read Better Auth's
  discovery document and JWKS over HTTPS, picks up a rotated key within about 30 minutes, and
  bills third-party monthly active users. If it gives trouble, the shared signing key is the
  verified fallback and changes only the signer.
- **Cost differs from the current stack in three places.** Compute is always on and billed per
  project and per branch (the Pro plan's credits cover one Micro project). Files moved from R2 to
  Supabase Storage start paying for downloads ($0.09 per GB beyond 250 GB a month on Pro; R2
  charges nothing for egress). Third-party monthly active users are billed beyond 100,000 on Pro.
  The hosted checklist must include a decision on the Spend Cap: on, an exceeded quota stops that
  service until the next cycle; off, it is billed.
- **Local trust relies on observed behaviour.** The emulator accepting a public-only key in its
  keys file is not documented. The stack suite covers it, so a CLI release that changes it fails a
  test instead of failing in use.
- **Privileged steps inside scoped transactions.** The `app.broadcast` wrapper and the jobs
  adapter's role reset bypass RLS by design. The wrapper stays in the non-exposed `app` schema,
  with `search_path = ''` and execute revoked from `public`; the role reset lives only in the jobs
  adapter and always restores the role.
- **pg-boss outside the migration stream.** It creates and upgrades the `pgboss` schema itself at
  boot. `supabase db reset` drops it and the next boot recreates it; schema diffs must be limited
  to `public`, `better_auth` and `app` so they do not capture it.

## Later, once this lands

Presence (who is online in an organization), broadcasting file and artifact events to refresh
lists, embeddings for files through a file subscriber and pgvector, and Supabase Branching for
preview environments.
