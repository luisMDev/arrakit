What I would do next, by priority

1. Make credits, storage + jobs, MCP/OAuth and billing optional. Drop the plans CHECK from the SQL.

Production

- No rate limiting shared across instances (Better Auth configures neither `rateLimit` nor
  `secondaryStorage`), and no audit log. The web has no full CSP (no `script-src`/`connect-src`;
  it would need nonces in TanStack Start and testing against Stripe, and its `connect-src` must
  allow the Supabase origin over https and wss for Realtime).
- No admin panel, customer API keys, seed data or data export (GDPR).

Frontend

- The landing copy is written in `apps/landing/src/pages/index.astro` (still placeholder text) and
  the landing does not share the web's theme.
- The sidebar's collapsed state is not restored on reload: shadcn writes the `sidebar_state`
  cookie, but nothing reads it during SSR. The sheet's screen-reader title ("Sidebar") comes in
  English from `components/ui/sidebar.tsx`.

Starting a new product

- `pnpm init:project` renames the product name, slug and npm scope. Two of the renamed values are
  functional: the slug prefixes the session cookie (`COOKIE_PREFIX` in `packages/auth/src/config.ts`)
  and the Stripe price lookup keys (`PRICE_KEY_PREFIX` in `apps/api/src/billing/subscription-plan.ts`).
  Renaming after the prices exist means creating them again; the script warns about both. The
  slug is also the local stack's `project_id`, which names its containers and volumes, so the
  renamed project starts with an empty database and the old stack must be stopped by its old id
  (the script warns about that too).

Hosting

- The README's hosted checklist has never been run. The Custom OIDC trust in particular is
  unproven outside the emulator: Supabase must read Better Auth's discovery document and JWKS
  over HTTPS. If it gives trouble, a signing key generated by the Supabase CLI and shared with the
  API is the fallback, and it changes only the signer.
- The local trust relies on the emulator accepting a public-only key in its keys file
  (`supabase/signing_keys.json`). That is observed behaviour, not a documented feature;
  `pnpm test:stack` pins it, so a CLI release that changes it fails a test.

Storage

- Nothing sweeps objects that have no row (an upload whose row was already gone, a failed delete).
- Storage calls have no request timeout; only the health probe is raced against three seconds.

Database

- Every organization operation costs a `begin`, a claims statement and a `commit`. Measure before
  optimising.
- pg-boss manages its `pgboss` schema outside the migrations: a database reset drops it until the
  API boots, schema diffs must stay limited to `public`, `better_auth` and `app`, and the
  advisors' warnings on its six functions (mutable `search_path`) are accepted.
- Tests run on PGlite, a newer Postgres major and a superuser, while the stack's role is not a
  superuser. The stack suite and e2e are the check for that drift, and for the PGlite stand-in for
  Realtime.

Later

- Presence (who is online in an organization), broadcasting file and artifact events to refresh
  lists, embeddings for files through a file subscriber and pgvector, and Supabase Branching for
  preview environments.

Backend

- A new module touches many places (schema, scope, contract, router, permissions, MCP tools,
  screen, navigation, i18n, tests). Workspaces is the reference module to copy; nothing generates
  the pieces.
- Coupled product pieces:
  - Credits are part of every procedure's base contract: the `PAYMENT_REQUIRED` error with its
    metric in `packages/contract/src/common.ts`.
  - The plan's seat count is part of member management (`packages/auth/src/organization.ts`).
  - Plans are fixed by a SQL CHECK (`organizations_plan_check` in
    `packages/db/src/schema/organizations.ts`), so changing them needs a migration.
- Files: no folders, no moving between the organization and a workspace, no previews and no
  malware scanning (a file subscriber is the place for it). Every plan has the same file policy.
  The type is checked by extension; the bytes are not inspected. An object whose delete fails
  stays in the bucket (logged). An upload link binds neither size nor type, so until it lapses a
  pending file can hold up to the bucket limit (50 MB) while only its announced size counts
  against storage, and nothing limits how many uploads a member reserves: storage use can exceed
  the plan by up to 50 MB per pending file for three hours (a cap on pending uploads per member,
  or counting a pending file at the policy's limit, is the fix). A pending upload, and one whose
  bytes did not match, holds its storage reservation for those three hours. Uploads are a single
  PUT (no resumable upload), so a dropped connection starts over.
- Tasks: no tracked job exists yet, so no journey starts one end to end. Tasks cannot be
  cancelled, there is no limit on concurrent tasks per organization, and `result` has no shape
  the web shows (a download link, for one). Realtime signals are not kept for a browser that is
  away: joining a channel reads the lists again. A permission change reaches Realtime when the
  token is next refreshed (at most 10 minutes). `realtime.send` turns its errors into a warning,
  so a lost signal is not reported.
- Hard to remove: credits, MCP/OAuth (`createApp` in `apps/api/src/app.ts` always mounts the MCP
  routes; no setting turns them off) and, above all, multi-organization mode.
