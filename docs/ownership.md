# File ownership per feature module

Each feature module edits only the files and directories it owns, so modules can be built in
parallel without merge conflicts. Every procedure, table, route, screen, locale file and email
template already exists, so **no module needs to edit a shared file**.

New files inside an owned directory are fine (for example `apps/api/src/billing/billing-service.ts`).
Tests live next to the code they test and belong to the same owner.

| --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| `packages/db/src/open-data.ts`, `packages/db/src/organization/index.ts`, `packages/db/src/index.ts` | Compose the per-domain `data/*` and `organization/*` modules; signatures change inside those modules (`organization/index.ts` also holds the organization, billing, roles, teams and storage scope: each owner edits only its entries). | `packages/contract/src/index.ts`, `packages/contract/src/common.ts`                                 | Compose module contracts (`billing.ts` holds billing and top-up); `index.ts` also declares `authProviders`, `onboarding`, `teams` and `plans`, edited only by their owners                                                                                                                                                                              |

If a module truly needs a shared file changed, it stops and reports it instead of editing.

## Cross-module contact points

- **Org deletion** (organizations-members) calls `deps.stripe.endNow()` (billing gateway interface)
  and `queueStoragePurge()` from `apps/api/src/workers/storage-purge.ts` (platform).
- **Invites** (organizations-members) send the magic link through `deps.auth.api.signInMagicLink`;
  the MailMember choice lives in `packages/auth/src/magic-link.ts` (auth-onboarding) and uses
  `memberEmail` (organizations-members) and `invitationFor` (organizations-members).
- **Member removal / org deletion** call `revokeGrants()` (organizations-members), which MCP
  (platform) relies on.
- **Settings > Billing** (billing) embeds the usage cards and Add credits dialog from
  `apps/web/src/components/usage/` (usage-credits).
- **`me.get`** is implemented in `apps/api/src/routers/account.ts` (organizations-members); the
  guards (auth-onboarding, shell-landing) only read it.
- **Workers**: a module that adds a queue puts its register function in its own file under
  `apps/api/src/workers/` and asks platform to add the one line in `apps/api/src/main.ts`.
